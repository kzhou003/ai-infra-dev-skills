# 报告大纲（code-wiki 风格）

`##` 是章（PDF 里每章新起一页，出现在左侧目录），`###` 是节。章名可以按项目调整，主干保持不变。

## 0. 怎么读这份导读（简短）
写给谁、读完能做什么、章节顺序（一个列表），以及固定的版本，放在 `::: callout key` 里。

## 1. 全景：问题、目标、限制
- **没有这个项目时有什么问题？** 用一张 2–4 行的表：环节、问题、谁来解决。
- **一张总图**：系统和它的周边（用户、上游数据、外部服务、其他仓库）。开源和闭源部分在视觉上区分开（闭源或外部用 `k=dark`）。
- **要求 / 目标 / 限制矩阵**：一张表，每个项目（或每个主要子系统）一列。行：核心目标、功能要求、规模压力、外部限制、关键解决手段、许可证。这张表是整份报告的骨架，后面每一章都在解释某个限制是怎么被解决的。
- 整个系统最多一个类比。

## 2–N. 每个主要组件一章
沿主数据路径排列。每章回答：
1. **职责**：它负责什么，两句话。
2. **难点**：是什么限制逼出了现在的设计（规模、延迟、故障、兼容性、不可信输入……）。
3. **原理**：机制本身，配图。结构用 `::: flow`，随时间展开的过程用 `::: steps`。每一跳都链到代码。
4. **契约**：关键类型和接口，用表格（名字、作用、关键字段、链接）。
5. **连接**：谁调用它、它调用谁、跨边界的数据是什么、什么格式。
6. **容易误解的地方**：贡献者容易踩的一两个坑（缓存存的是原始输出、懒加载、中间件顺序……）。

常见组件：入口与启动、路由/分发、核心引擎、存储与缓存、同步/状态、插件或扩展系统、输出/渲染、部署形态与配置。

## 端到端生命周期
挑一个具体请求，穿过所有组件，用带编号的 `::: flow` 或 `::: steps` 讲一遍。标出哪一步在哪个仓库，哪一步不公开。

## 开源许可证（读者可能 fork、分发或部署时）
- 表格：部分、许可证、证据链接（LICENSE、包清单、README 里的例外条款）。
- 用大白话讲许可证的核心规则（AGPL 要讲网络条款）。
- 场景表：自用 / 给上游提 PR / 公开 fork / 发安装包 / 对外提供服务 / 上架应用商店 / 闭源复用 → 允许吗？要做什么？
- 历史：许可证什么时候改过（用 GitHub API 核实），已经发布的旧版本仍然适用旧许可证。
- 例外：素材、图标、字体、商标、CLA。结尾注明“不是法律意见”。

## 贡献与定制
- 开发环境命令（照抄 CONTRIBUTING，并核实存在）。
- 项目的 review 规则（AGENTS.md、lint、测试、PR 模板），做成简短的清单。
- 适合入手的方向，以及需要避开的方向（比如依赖未公开服务端接口的功能）。
- 定制路线：一张小图 + 一张表（fork 客户端、自建、插件、agent 工作流），写清代价和依赖。

## 附录：源码索引
每个仓库一张表：主题 → 固定链接。这是读者以后最常回来翻的部分。

## 篇幅参考
中等规模项目（一两个仓库、约 10 万行）：6–9 章、8–16 张图、2–4 个类比、60–150 个源码链接、PDF 15–30 页。
