# 读懂一个代码库 → code-wiki 式报告（HTML + PDF）

交付物是一个自包含的 HTML 页面，风格像 code wiki：左侧目录，章节从“为什么需要它”一路讲到“是哪一行代码”，大量小图、少量精准的类比、密集的源码链接；再从同一个页面打印出 PDF。读者是有经验、但第一次接触这个代码库的工程师，他的目标是**贡献代码或在它之上定制**。按这个读者来写。

需要的东西都在本 skill 里：

| 路径（相对本 skill） | 作用 |
|---|---|
| `toolkit/run.sh` | 用带 `markdown-it-py` 的 Python 运行工具脚本（首次使用时自动建一个私有 venv） |
| `toolkit/build_report.py` | `report.json` + Markdown → `report.html`（可加 `--pdf` `--shots` `--links` `--strict`） |
| `toolkit/shots.py` `make_pdf.py` `check_links.py` | 图的截图、用 headless Chrome 出 PDF、外链检查 |
| `reference/syntax.md` | **写之前先读**：容器语法、流程图 DSL、逐步演示动画、固定版本的源码链接 |
| `reference/outline.md` | 章节模板，以及每章必须回答的问题 |
| `reference/checklist.md` | 质量标准；回复用户之前逐条过一遍 |
| `examples/rsshub-folo/` | 完整的、已验证过的范例（RSSHub + Folo 导读：14 张图、159 个固定链接） |

## 流程

### 1. 确定范围（别过度提问）
默认：整个项目、面向贡献者、中文。只有目标确实有歧义（比如多个同名仓库）时才问。用户提到两个相关项目（引擎和它的客户端、库和使用它的服务）时，两个都讲，并加一章讲它们怎么连起来。

输出放在单独的目录，默认 `~/development/<主题>-report/`，**不要放进被分析的仓库里**。文件名：`report.json`、`report.md`、`report.html`、`report.pdf`。

### 2. 拿到源码并固定版本
- clone 每个仓库（只读代码用 `git clone --depth 1` 就够），记下 `git rev-parse HEAD`。所有源码链接都固定到这个 SHA，写在 `report.json → pins` 里，`local` 指向本地 clone，构建时用 `git show` 读文件（快、离线、不受工作区改动影响）。
- 凡是涉及**历史**的说法（许可证什么时候改的、某功能什么时候加的），浅 clone 不够：用 GitHub API（如 `gh api 'repos/O/R/commits?path=LICENSE'`）或取旧 SHA 的文件核实。不要凭记忆写历史。
- 用一句话告诉用户范围和固定的 SHA，然后继续。

### 3. 研究：像新来的维护者那样读
按顺序过一遍，记下精确的 `path:line`：
1. `README`、`CONTRIBUTING`、`AGENTS.md` / `CLAUDE.md`、`LICENSE`（以及各子包的 `license` 字段、NOTICE、图标/素材/商标例外）、文档目录。
2. 清单与构建：package.json / pyproject / Cargo.toml / CMake、workspace 结构、脚本；怎么构建、运行、测试、部署。
3. **入口**：主进程 / 服务启动、CLI 入口、对外 API。
4. **一条真实请求或数据的完整路径**：挑一个具体调用（一次 HTTP 请求、一次 `generate()`、一次编译），穿过每一层，记下每一跳的文件和行。它是整份报告的主干。
5. 核心抽象：其他代码都依赖的 3–8 个类型/接口。
6. 状态与存储：缓存、数据库、队列、同步、生命周期与清理。
7. 配置与部署形态，以及每种形态带来的限制。
8. 扩展点：贡献者在哪里加东西（插件、路由、算子、后端），以及对应的 review 规则。
9. **仓库里没有的东西**：闭源后端、依赖的 SaaS、生成代码、二进制。想定制的读者最需要知道这个。

每个不显然的说法都去代码里核实：默认值（读配置代码）、行号、谁调用谁。推断出来而不是读到的内容，在正文里明确标出（“客户端只能看到 API，服务端不在公开仓库里”）。

### 4. 大纲
按 `reference/outline.md`。主干固定为：
**导读 → 要求/目标/限制表 → 架构总图 → 每个主要组件一章 → 端到端生命周期 →（许可证）→ 贡献与定制 → 源码索引。**
每个组件章节回答：*它解决什么问题、什么限制让它难、怎么解决的、和相邻组件怎么连、代码在哪。*

### 5. 写 `report.md` + `report.json`
先读 `reference/syntax.md`。最重要的规则：
- **图**：每个主要概念一张，一份报告通常 8–16 张。架构和数据路径用 `::: flow`，随时间展开的过程用 `::: steps`（每一步高亮相关节点）。节点标题要短（约 ≤ 11 个汉字 / 18 个拉丁字符），副标题 ≤ 约 14 个汉字，边上的标签 1–3 个词。每张图都有图注，说明该看什么，并带源码链接。
- **类比**：全文 2–4 个，每个对应一个具体机制，把映射关系写明（书架 = block，借书卡 = block table）。不做装饰，一节最多一个。
- **源码链接**：每个具体说法旁边都放 `[[alias:path#Lx|标签]]` 或 `[[alias:path@Symbol|标签]]`；优先用 `@Symbol`（行号写错也能自动纠正）。一份报告通常 60–150 个。
- 对比和“要求/目标/限制”用**表格**；推理用正文。
- **代码片段**：短、简化，并标注“简化自 <链接>”，不要贴大段文件。
- 只要读者可能 fork、分发或部署，就写**许可证章节**：各部分的许可证和证据、场景表（自用 / 提 PR / 公开 fork / 发安装包 / 对外提供服务）、特殊例外（素材、图标、商标）、CLA、许可证历史。注明“不是法律意见”。
- **中文写法**：用平实的中文讲清楚，避免翻译腔和空话；技术名词和标识符保留英文并用 `code` 样式；引号用“”；一句话只讲一件事。

### 6. 构建、看图、修改（循环到干净为止）
```bash
bash <skill>/toolkit/run.sh build_report.py <out>/report.json --strict --shots
```
- `--strict` 遇到以下情况都会报错退出：链接无法解析、文件或符号不存在、行号超过文件长度、节点重叠、文字超出方框、边标签放不进两个节点之间的空隙，以及 `report.json → quality` 里的数量下限。
- **逐张打开 `<out>/.shots/` 里的 PNG 去看。** linter 看不出连线交叉、连线穿过节点、布局让人看不懂这类问题。修法：挪动节点（`col`/`row` 可以是小数）、指定连接边（`a:b -> c:t`）、加大 `cw`/`rh`，或者把标签挪到图注里。改完重新构建、再看。
- 然后 `--links`（所有外链返回 200）和 `--pdf`。看一下页数，并抽查两三页（有 `pdftoppm` 的话：`pdftoppm -r 45 -png -f 3 -l 5 report.pdf /tmp/p`）。

### 7. 回复用户
给出 HTML 和 PDF 的路径、报告覆盖了什么（每章一句话）、固定的 SHA、做过哪些验证（链接检查、逐张看图），以及没能核实的说法。如果宿主环境支持发布页面（Artifact 工具），用一句话询问是否需要；不要擅自发布。用户没要求就不要 commit 或 push。

## 不要做的事
- 不要逐个文件罗列目录树：讲职责和连接关系，然后给文件链接。
- 没在固定 SHA 的代码里核实过的话，不要写。
- 不要从改动过的工作区手算行号：pins 读的是固定 commit，用 `@Symbol` 让构建器去解析。
- 没看过截图的图不要交付。
- 不要写空话（“这是一个强大的框架”）。每一段都应该讲出这个代码库特有的东西。
