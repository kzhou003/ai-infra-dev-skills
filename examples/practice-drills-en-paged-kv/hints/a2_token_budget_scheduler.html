A2 · Scheduler step: token budget, chunked prefill, FCFS admission

One scheduling step of a continuous-batching engine: hand out a fixed token budget, running requests first, then new prompts in arrival order, splitting long prompts into chunks.

Files: mine/a2_token_budget_scheduler.py your code · tests/test_a2_token_budget_scheduler.py tests · solutions/a2_token_budget_scheduler.py solution

The drill in one minute

  • Where it lives: the engine calls schedule() once per forward pass; the result is the batch. In vLLM v1 this is Scheduler.schedule.
  • You implement: Scheduler.__init__, add, schedule() -> {req_id: num_tokens} and update(scheduled) -> finished ids. Request is given.
  • One formula drives everything: a request needs num_tokens − num_computed_tokens more tokens, where num_tokens = prompt + generated. That is the rest of the prompt while prefilling and exactly 1 while decoding.
  • Rules: running first, in order · then waiting FCFS while budget > 0 and len(running) < max_num_seqs · each request gets min(need, threshold, budget) · a request becomes running with its first chunk · never skip the head of the waiting queue.
  • update: add the scheduled tokens to num_computed_tokens; if that caught up with num_tokens, one token is generated; at max_new_tokens the request finishes and leaves running.

Intuition

Analogy · Burner slots in a kitchen

Every minute the kitchen has 8 burner-slots. Dishes already on the stove each need one slot to cook their next bite, so they are served first. New orders get what is left, in the order they came in. A banquet order that needs 30 slots is cooked over several minutes instead of blocking the kitchen. And the kitchen never lets a small order jump ahead of a waiting banquet, or the banquet would wait forever.

Step through a small run

▶ budget 8, max_num_seqs 2, two requests
1. Step 1: a arrives (prompt 5, wants 3 tokens)

a needs 5 − 0 = 5 → gets 5. schedule() == {"a": 5}. After update, computed = 5 = num_tokens → a produces token 1 (num_tokens becomes 6).

2. Step 2: b arrives (prompt 20, wants 1 token)

Running first: a needs 6 − 5 = 1 → 1 → token 2. Budget left 7 → b gets min(20, 7) = 7 and becomes running. {"a": 1, "b": 7}. b produces nothing yet: 7 < 20.

3. Step 3: a finishes

a → 1 → token 3 = max_new_tokens → finished, leaves running. b needs 20 − 7 = 13 → gets the remaining 7 (computed 14). update returns ["a"].

4. Step 4: b finishes

Only b is running: needs 6 → gets 6 → computed 20 = num_tokens → first token → finished (max_new_tokens = 1). update returns ["b"]; step 5 schedules nothing.

Pitfalls

  • Treating decode and prefill as different code paths. One formula covers both; separate paths usually double-count or forget the token produced by the last prefill chunk.
  • Generating a token after a partial chunk. Only a pass that reaches num_tokens produces a token.
  • Skipping a blocked waiting request to admit a smaller one: passes a quick test, fails the FCFS test, and starves big prompts in production.
  • Checking max_num_seqs against waiting instead of running, or after appending.
  • Iterating over running while removing from it in update: iterate over a copy.
  • Forgetting the threshold applies to running prefills too, not only new ones.

Key questions

  1. What is need for a request that is decoding? For one halfway through its prompt?
  2. Why serve running requests before waiting ones?
  3. When the head of the waiting queue gets 0 tokens, do you try the next one?
  4. In update, how do you know whether this step produced a token for a request?
L2Approach and common trapsbreakdown & pitfalls (medium spoiler)
  • need = req.num_tokens - req.num_computed_tokens; cap with the threshold if 0 < threshold < need; then min(need, budget).
  • schedule: loop over running while budget > 0; then while waiting and budget > 0 and len(running) < max_num_seqs: popleft, compute n, append to running, record.
  • update: for each running request with n > 0: num_computed_tokens += n; if it equals num_tokens, num_output_tokens += 1; at max_new_tokens remove and report. Iterate over list(self.running).

Answers to the key questions
  1. Decoding: exactly 1 (the token generated in the previous step has no KV yet). Halfway: the rest of the prompt, possibly capped by the threshold and the budget.
  2. They already hold KV blocks and their users are waiting for the next token; starving them wastes memory and makes inter-token latency spiky.
  3. No. With budget > 0 the head always gets at least 1 token, so the loop only stops on budget 0 or max_num_seqs. Stopping instead of skipping is what makes the queue FCFS.
  4. Compare after adding: num_computed_tokens == num_tokens means the pass covered the last known token, so its logits are sampled.

"""A2 · One step of a continuous-batching scheduler with chunked prefill — reference solution.

The vLLM v1 scheduler does not have separate "prefill" and "decode" phases. Every request just has
`num_tokens` (prompt + generated so far) and `num_computed_tokens` (how many of those already have
KV in the cache); each step it hands out at most `token_budget` new tokens:

1. RUNNING requests first, in order. Each gets min(remaining, long_prefill_threshold, budget)
   tokens, where remaining = num_tokens - num_computed_tokens (1 for a decoding request).
2. Then WAITING requests, first come first served, while budget is left and fewer than
   max_num_seqs requests are running. A prompt bigger than the budget is split across steps
   (chunked prefill); the request becomes RUNNING as soon as it gets its first chunk.

`update(scheduled)` plays the model: it adds the scheduled tokens to num_computed_tokens, and a
request whose KV caught up with all its tokens samples one new token. A request that reaches
max_new_tokens finishes and leaves the running list.

API
    Request(req_id, num_prompt_tokens, max_new_tokens)               given (dataclass)
    Scheduler(token_budget, max_num_seqs, long_prefill_threshold=0)
        .add(req)                      append to the waiting queue
        .schedule() -> dict[str, int]  req_id -> tokens to run this step (insertion order = batch order)
        .update(scheduled) -> list[str]   apply one model step, return the finished req_ids
        .waiting (deque) / .running (list)
"""
from __future__ import annotations

from collections import deque
from dataclasses import dataclass


@dataclass
class Request:
    req_id: str
    num_prompt_tokens: int
    max_new_tokens: int
    num_computed_tokens: int = 0    # tokens whose KV is already in the cache
    num_output_tokens: int = 0      # tokens generated so far

    @property
    def num_tokens(self) -> int:
        """All tokens of the sequence so far: prompt + generated."""
        return self.num_prompt_tokens + self.num_output_tokens


class Scheduler:
    def __init__(self, token_budget: int, max_num_seqs: int, long_prefill_threshold: int = 0) -> None:
        self.token_budget = token_budget
        self.max_num_seqs = max_num_seqs
        # 0 = no cap. A cap stops one huge prompt from taking the whole step and stalling every
        # decoding request behind it (vLLM: scheduler_config.long_prefill_token_threshold).
        self.long_prefill_threshold = long_prefill_threshold
        self.waiting: deque[Request] = deque()
        self.running: list[Request] = []

    def add(self, req: Request) -> None:
        self.waiting.append(req)

    def _tokens_for(self, req: Request, budget: int) -> int:
        n = req.num_tokens - req.num_computed_tokens          # 1 while decoding, the rest of the prompt while prefilling
        if 0 < self.long_prefill_threshold < n:
            n = self.long_prefill_threshold
        return min(n, budget)

    def schedule(self) -> dict[str, int]:
        budget = self.token_budget
        out: dict[str, int] = {}

        # 1. RUNNING first: they already hold KV blocks, and starving them wastes that memory and
        #    hurts inter-token latency. Order matters only when the budget runs out mid-list.
        for req in self.running:
            if budget == 0:
                break
            n = self._tokens_for(req, budget)
            if n > 0:
                out[req.req_id] = n
                budget -= n

        # 2. WAITING, FCFS. Stop (don't skip) when a request cannot be admitted: skipping would let
        #    later small requests overtake an earlier big one forever (starvation).
        while self.waiting and budget > 0 and len(self.running) < self.max_num_seqs:
            req = self.waiting.popleft()
            n = self._tokens_for(req, budget)
            self.running.append(req)        # RUNNING from its first chunk on
            out[req.req_id] = n
            budget -= n

        assert budget >= 0 and len(self.running) <= self.max_num_seqs
        return out

    def update(self, scheduled: dict[str, int]) -> list[str]:
        finished: list[str] = []
        for req in list(self.running):
            n = scheduled.get(req.req_id, 0)
            if n == 0:
                continue
            req.num_computed_tokens += n
            # A forward pass only yields a usable next token when it covered the LAST known token:
            # a partial prefill chunk produces logits nobody samples from.
            if req.num_computed_tokens == req.num_tokens:
                req.num_output_tokens += 1
                if req.num_output_tokens >= req.max_new_tokens:
                    self.running.remove(req)
                    finished.append(req.req_id)
        return finished
